# Fairfax Industries — Roadmap from the 2026-06-26 planning session

## Context

This was a planning + research + discussion session — **no code changes**. It was
prompted by a community-needs research doc (`docs/research/2026-06-26-community-needs.md`)
and a friend's critique that the tool "seems useless — high-rank players already know
this." We tested that critique, ran competitive research on **deadlocklabs.gg** and
**statlocker.gg/builds**, and decided what to build next.

**Core finding:** the community-needs doc argues the winning move is to stop competing on
"calculate my build" and compete on "win the matchup" — and the app's *already-locked*
attacker-vs-target model sits exactly in that white space. So the direction is **validation,
not redirection**: double down on two-sided combat, extend it into lane-scoped
counter-building, fuse in empirical data, lift specific UX ideas from the competitors,
sharpen positioning, and stay free/static. Plus three concrete polish fixes.

This document is the **roadmap**. Each major feature will get its own detailed spec
(brainstorming → writing-plans) in a follow-up session **before any code is written**.

---

## Strategic decisions locked this session

- **Fuse sim + empirical.** Sim (first-principles combat math) stays the core; empirical
  aggregates *amplify* it. Empirical proposes (candidate counters, average builds), the sim
  proves (exact TTK/EHP deltas, breakpoints). **Never become a match tracker** — no
  leaderboards, match feeds, recent/active matches, rank distribution, or personal match
  history. Empirical data is used *only* in service of a build decision.
- **Monetization:** free + donations; **stay static** (no accounts, no backend, no runtime
  DB); **no ads**. A pro "team workspace" tier (saved team lanes, combo solver, shared
  libraries) is a *future maybe* — and would gate *workflow*, never the core math.
  Principle: **never paywall a number, only ever a workflow.**
- **Positioning:** lead the front door with Lane Lab ("what do I build to beat this lane"),
  keep the sim depth (breakpoints, TTK, execute) as the credibility proof underneath.

## Research appendix (key facts that constrain the build)

- **`deadlock-api.com` is the shared, free, no-auth upstream.** Both deadlocklabs.gg and
  statlocker.gg are essentially presentation layers over it; statlocker runs *no* proprietary
  analytics pipeline. The same data is available to us — and we already sync static game data
  from it. So win-rate/pick-rate/matchup data is **commoditized; differentiation is product/UX,
  not data access.**
- **Relevant endpoints:** `/v1/builds`, `/v1/analytics/hero-build-stats/{hero_id}`,
  `/ability-order-stats`, `/item-stats` (supports `enemy_hero_ids`, `same_lane_filter`,
  `item_order`, `min/max_bought_at_s`), `/hero-counter-stats`, `/hero-synergy-stats`.
  Rank bracket via `min_average_badge`; patch filtering via date window; `min_matches` floor
  to suppress small-sample noise; win rate = `wins/(wins+losses)` computed client-side.
- **Statlocker's core trick:** a build page = authored build content + real-world performance,
  joined on the stable `hero_build_id`.
- **Our data layer today:** `scripts/sync-deadlock-api.ts` bakes only static game data
  (heroes/abilities/items/stat-mods/rank profiles/2 snapshots) into
  `src/lib/baked-data.json` (~313KB, committed, imported at build time). **No runtime DB.**
  A daily GitHub Action (`.github/workflows/sync-data.yml`) re-syncs and commits on change.
  The sync is extensible (~3–4h per new endpoint). Empirical data must be **baked** —
  bake a curated subset, likely in a *separate* JSON loaded only on `/hideout`, to limit
  bundle bloat.
- **The engine is ready for counter-scoring.** `simulate(build, target, opts)` in
  `src/lib/sim/engine.ts` is a pure function returning `{burst, sustainedDps, timeToKill,
  theirEhp, abilities, ...}`. Counter ranking = loop candidate items, re-run `simulate`,
  rank by matchup delta. It is **strictly 1-attacker-vs-1-target** today — multiple enemies =
  call it per enemy (cheap); a lanemate contributing *combined damage* is a real engine
  expansion (deferred — see Lane Lab phasing).

## The roadmap

### Feature 1 — Lane Lab (centerpiece: lane-scoped counter-building)

The headline differentiator. Models a real Deadlock **lane**, not an abstract duel.

- **Setup:** pick your hero + (optional) lanemate, and 1–2 enemy laners.
- **v1 — Suggestions mode (the teacher):**
  - Inline counter chips on your build items — "good vs Seven," "good vs Warden" — each with
    a tooltip exposing the win-rate / counter numbers (from `hero-counter-stats` +
    `item-stats?enemy_hero_ids`).
  - Lanemate drives **synergy suggestions only** ("good with [lanemate]", from
    `hero-synergy-stats`); the **sim stays you-vs-each-enemy 1v1** (run `simulate` per enemy).
  - **Exact mode (the theorycrafter):** toggle suggestions off, hand-build exact loadouts for
    yourself *and* each enemy, all numbers resolving simultaneously with breakpoints.
  - **Inverted recommender:** drop in the exact build that just beat you → "this one item is
    the biggest lift to your EHP / damage vs them." (Loop `simulate` over candidate items,
    rank by EHP/TTK delta.)
- **v2 (fast-follow):** enemies auto-fill their **average build path**, progressing as your
  souls climb (reuses the existing soul-checkpoint progression scrubber in `hideout.tsx`).
  Heaviest data lift — distill per-hero `item_order`/`bought_at_s` into a canonical timeline.
- **Future / possible-pro:** full **combined-damage 2v2 combo solver** ("buy X+Y, land Q +
  lanemate's ability → guaranteed kill under N HP"). Niche/elite; the natural candidate for a
  future paid team tier. Requires multi-attacker engine expansion. See Parking lot below.
- **UI slot:** new "Counter"/"Lane" tab or a panel below the three lenses in
  `src/components/hideout.tsx`; preserves attacker scenario state, varies enemy items.
  Consider extracting a `useCounterBuild`/`useLaneLab` hook to keep the 1500-line component
  readable.

### Feature 2 — Empirical data layer (enabler for Lane Lab + the lifts)

Extend `scripts/sync-deadlock-api.ts` to also bake curated aggregates: `hero-counter-stats`,
`hero-synergy-stats`, `item-stats` (incl. `enemy_hero_ids`), `ability-order-stats`, and (for
v2) build-path/`item_order` aggregates. Add accessors to `src/lib/data.ts`; extend the daily
Action. Keep it baked-static; curate hard and consider a separate `/hideout`-only JSON to cap
bundle size. Be a good citizen (grab a free API key; consider sponsoring deadlock-api).

### Feature 3 — Lifted UX ideas (all adopted, tracker-free)

- **Two-axis item ranking** — popular-by-pickrate vs highest-winrate, side by side on `/items`
  and hero pages.
- **Build-path timeline overlay** — overlay the planned build vs the aggregate average,
  bucketed by minute/soul; reuses the progression scrubber.
- **Discovery sidebars** — Hidden Gems / Risers / Droppers / Sleepers — plus **ability-order
  win rates** ("which skill order actually wins") on hero pages.
- **Rich OG link previews** for `/b/<code>` — dynamic `opengraph-image` (hero-vs-hero +
  headline numbers) so build links unfurl in Discord. Highest-leverage virality win;
  not data-dependent — pull this early.

### Feature 4 — Positioning / front-door

- Re-lead the home page (`src/app/page.tsx`) around Lane Lab ("what do I build to beat this
  lane"), keeping the sim depth as proof. (Note: the front door is already matchup-framed —
  "Build it. Prove it.", "Test any matchup" — so this is evolution, not a rewrite.)
- **Seed a populated, resolved demo matchup** as the default `/hideout` state, so a first-timer
  sees live numbers + a who-wins read instead of an empty calculator.

### Polish / correctness fixes (from the bug list)

- **Avatar click opens the hero selector**, and replace the native OS scrollbar popup with an
  **embedded styled portrait-grid hero picker** (command-palette-style popover). Files:
  `src/components/hideout.tsx` (VersusBand portraits + selector).
- **Fire-rate-aware default shots** — default to ~1 second of fire = `round(hero fire rate)`
  instead of a flat 8 (Wraith ≈ 10, Abrams ≈ 1–2), still user-overridable. (Confirm the 1s
  window at build time.) Files: combat-scenario defaults in `hideout.tsx` /
  `SimOptions` in `src/lib/sim/types.ts`.
- **Default enemy target to matching level** — flip the existing `matchTargetLevel` default to
  on; keep "by items purchased" as the toggle-off.

## Parking lot — future pro: combined-damage 2v2 combo solver

Captured so we don't lose it. **Not scheduled for any near-term sprint** — a deliberate
"someday/maybe," and the leading candidate for a first paid tier if monetization ever happens.

**What we discussed.** Whether the lanemate should contribute *combined damage* in the sim
(true 2v2 math) or merely drive synergy suggestions. The compelling case is elite/pro: teams
with fixed lane duos who know exactly what their partner buys and does — e.g. "if Abrams buys
X+Y and lands Q, comboed with the lanemate's ability, can we *guarantee* a kill on anyone
under N HP?" That's a **combo solver** that searches for guaranteed-kill sequences across two
kits and two itemizations.

**Decision.** v1 lanemate = **synergy suggestions only**; the combined-damage combo solver is
**deferred to a future phase**, outside the next sprint. If a paid "team workspace" tier ever
happens, this is its flagship feature.

**Why.**
- Genuinely useful but genuinely **niche** — exact 2v2 breakpoints serve a small elite/pro audience.
- It's the one place the friend's "high-rank players already know this" critique **fully
  collapses** — nobody hand-computes guaranteed-kill 2v2 combos — so it's defensible value, but
  for few people.
- Requires a real **engine expansion**: the sim is strictly 1-attacker-vs-1-target today;
  combined damage means multi-attacker modeling (timing/sequencing of two kits), not addition.
- Fits the monetization principle — **never paywall a number, only a workflow.** The *math*
  stays free; what could be paid is the *workspace* around it (saved team lanes, the solver,
  shared libraries, team accounts), which also keeps the app static until real demand justifies
  accounts/backend.

**Left open for the future.**
- Is combined-damage 2v2 worth the engine expansion at all, and is it the *first* pro-tier feature?
- How to model combo **sequencing/timing** — windups, animation locks, travel time, order of
  operations — the solver needs a sequencing model, not just additive damage.
- Precise definition of "guaranteed kill" (from full HP? accounting for enemy reactions/items/escapes?).

**Known blockers / risks.**
- Engine is 1v1 — multi-attacker is a **structural** change, not an additive one.
- Combo sequencing/timing is genuinely **hard to model accurately**, and that's exactly where
  the project's "trustworthy numbers" claim is most at risk.
- A paid tier means **accounts + billing + backend** — a category change from today's
  static/no-DB architecture; only worth it post-traction.
- **Small audience → low direct revenue**; value is more credibility/halo than money.
- Empirical synergy data is **hero-keyed**, so it can't validate specific combo *builds* — the
  solver would lean almost entirely on the sim.

## Parking lot — Lane Lab future / pro enhancements

Captured 2026-06-26 during Lane Lab v1 design. v1 ships the **suggestion layer** (a "Counter"
tab) on the existing 1-enemy workbench, built lane-ready. These are the deliberate upgrades
beyond it:

**Pro-lane setup (the polished full lane).** The eventual target is the polished multi-entity
lane (Option 2): you + lanemate vs 1–2 enemy laners, suggestions↔exact, lanemate synergy chips,
per-enemy results. Lane Lab v1 is built as its foundation (enemy-array state capped at 1,
enemy-parameterized accessors/components) so v1.x lifts the cap *additively*. This is also the
natural home for a future "team workspace" pro tier (saved team lanes, shared libraries) — gate
workflow, never the math.

**Exhaustive (brute-force) recommender — pro.** v1's recommender sim-ranks a *bounded* candidate
pool (the empirical counter items, ~15) for instant results. A future "thorough" mode would run
`simulate()` over **every** item (~150+) for the provably-optimal counter, accepting longer
compute — likely off the main thread (web worker) + a progress indicator. Trades latency for the
absolute-right answer; valued by pros who want certainty over speed. Cheap to add later (the
engine is pure; it's just a bigger loop + a worker).

**Full empirical dataset — pro.** v1 bakes a *curated* subset (top-N counter items per pair,
~370 KB gzip, one client JSON). The full set is practical but **not** as one client file:
- Full counter-item data (all 38×38 pairs) ≈ **49 MB raw**; full build-path flow ≈ **73 MB raw**.
- Practical delivery = **lazy-loaded per-key files** — one small file per `(hero, enemy)`
  matchup (~5 KB gzip) / per hero (build-path), fetched on demand. Full fidelity, tiny
  per-view download.
- Caveat: 49 MB re-synced **daily** would bloat git history if committed — so the full set
  likely wants to be **generated at deploy** (or git-LFS / a non-tracked artifact), not committed
  like the curated file.
- Verdict: a clean future upgrade for pros who want every matchup's exact data, same static/edge model.

## Revised direction (2026-06-26, after Lane Lab v1 shipped)

Post-v1 feedback from the product owner reshapes the next phase:

1. **Counter logic must be cost- and phase-aware.** v1's recommender ranks by raw duel-shift,
   so it always surfaces 6,400 (tier-4) items — useless for laning, where the question is "best
   counter I can *afford right now*." Rework to rank by **value within a soul budget**
   (value-per-soul) and **scope to the laning phase** (early tiers; anti-heal / resist / slow
   effects that matter in a 2v2). Use the spike's **purchase-timing** (`avg_buy_time_s`) and
   **build-path** data as the affordability/phase signal. (Supersedes the earlier
   "level-isolated marginal eval" framing — affordability, not level-isolation, is the real fix.)

2. **Split `/hideout` into two focused surfaces** (supersedes "full lane as a tab"):
   - **Damage calculator** — today's workbench stays a clean "Path of Building": hero + items →
     exact damage/DPS/EHP/breakpoints vs a target, at any point in the game.
   - **Lane matchup calculator** — a *dedicated page* (not a tab): you (+ lanemate) vs enemy
     laner(s), with affordable/phase-appropriate counters + synergy, driven by the empirical+sim
     fusion. **Lane Lab graduates from the Counter tab to its own surface** (its original vision).
     The v1 Counter tab is the seed; the v2 build-path / auto-enemy data lands here.

   This resolves the awkwardness of cramming a 4-entity lane into the workbench's tab strip and
   lets each tool excel at one job. Wants its own brainstorming → spec session.

## Verification / how each piece gets validated

This session produces no code; verification is per-feature in later sessions. For each:
run `bun test` against `src/lib/sim/engine.test.ts` for any engine change; stress-test
matchup numbers against the in-game practice range (the project's accuracy moat); confirm the
baked-data sync produces valid JSON and the bundle stays within budget; and manually exercise
the new UI in `/hideout`.

## Open questions to resolve at spec time

- Exact engagement window for default shots (1s vs slightly longer).
- Bundle-size budget for baked empirical data; separate JSON vs inline.
- deadlock-api's granularity/availability for per-soul build-path aggregation (gates Lane Lab v2).
- Whether combined-damage 2v2 is worth the engine expansion, and if it's the first pro-tier feature.
